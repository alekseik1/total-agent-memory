# Серверная память 14.0.0

Отдельные SQLite-хранилища для личной памяти каждого человека, каждой команды и общей памяти. Сервер объединяет разрешённый поиск. Графы, индексы и кеши существующего Store/Recall изолированы процессами. Локальный stdio-режим сохраняется.

## Возможности и права

- По умолчанию запись личная; поиск охватывает все доступные области. Область передаётся структурой `scope`, например `{"kind":"team","team_id":"engineering"}`. Тематические теги не расширяют доступ.
- Участник команды имеет роль `reader`, `editor` или `manager` (руководитель отдела: пишет как editor и видит активность сотрудников). Общую память читают и редактируют все аутентифицированные пользователи этого сервера, включая тех, у кого в командах роль `reader`: общая область открыта всей компании, а роли `reader`/`editor`/`manager` ограничивают только командные области. Каждая правка пишется в историю с автором. Административные изменения выполняются через локальную CLI или веб-панель `/dashboard/` (роли организации `member`, `company_viewer`, `superadmin`, вход по паролю через одноразовый код приглашения, ключи провайдеров) — см. [TEAM_DASHBOARD.md](TEAM_DASHBOARD.md) (English).
- Автор и название клиента берутся из личного токена. Хранятся только хеши токенов; токен можно отозвать. Членство и токен проверяются на каждом запросе и перед отправкой работы в процесс.
- Правка создаёт новую версию записи; возвращённый новый ID использовать дальше. Исходный автор сохраняется. `expected_revision` защищает от затирания чужих правок. История включает предыдущие версии, автора, время UTC, причину и состояния до/после.
- Изменение записи и аудит выполняются в одной транзакции. История сохраняется после мягкого удаления. Для прежних записей без автора используется `Legacy / unknown`.
- `memory_export` и `memory_history` постраничные; `after` — последний ID записи или sequence события соответственно.
- `memory_save`, `memory_update`, `memory_delete` принимают необязательный `request_id` (UUID). Повтор того же запроса от того же пользователя в той же области (`scope`) возвращает прежний результат. Другой payload с этим UUID в той же области отклоняется. UUID и результат сохраняются в базе этой области, в одной транзакции с записью; поэтому учёт `request_id` действует внутри одной области. Тот же UUID в другой области не распознаётся: запрос выполняется заново. При повторе после timeout нужно сохранить исходные аргументы, область и UUID.

Удалённый каталог сейчас содержит восемь инструментов: `memory_scopes`, `memory_save`, `memory_recall`, `memory_get`, `memory_update`, `memory_delete`, `memory_history`, `memory_export`, инструменты обучения отделов `onboarding_*` — см. [TEAM_ONBOARDING.md](TEAM_ONBOARDING.md), а также отчёт `memory_report` (личный, по отделу или по компании — см. [REPORTS.md](REPORTS.md)). Локальный каталог из77инструментов сохранён. Произвольные операции чтения файлов серверной машины удалённо не предоставляются. Перенос/публикация существующей записи между областями пока не входят в этот каталог; явное сохранение в выбранной области работает.

Авторизация — предварительно выданные личные Bearer-токены. Интерактивный OAuth-вход не реализован. Для клиента без настройки HTTP-заголовков используйте stdio-мост ниже. Внешний сервер публикуйте через HTTPS reverse proxy; HTTP оставлен для локального соединения.

## Сервер из Python-пакета

После установки собранного wheel:

```sh
tam-team --root /path/to/team-data user-add vasya 'Вася'
tam-team --root /path/to/team-data user-add petya 'Петя'
tam-team --root /path/to/team-data team-add engineering 'Разработка'
tam-team --root /path/to/team-data member vasya engineering editor
tam-team --root /path/to/team-data member petya engineering editor
tam-team --root /path/to/team-data token-create vasya --client codex --out /path/to/vasya.token
tam-team --root /path/to/team-data serve --host 127.0.0.1 --port 3738
```

Токен записывается в новый файл с правами0600; существующий файл не перезаписывается. Для второго пользователя создать отдельный токен. Отзыв: `tam-team --root /path/to/team-data token-revoke --file /path/to/vasya.token`. Удаление членства: `tam-team --root /path/to/team-data member petya engineering remove`. Увольнение: `tam-team --root /path/to/team-data user-disable petya`. Команда не требует файлов токенов: она отзывает все токены пользователя, завершает его сессии в dashboard, аннулирует неиспользованные коды приглашения и блокирует вход; последнего активного superadmin отключить нельзя. Тот же путь использует кнопка Disable в dashboard. Командные записи и авторство сохраняются; личная область остаётся на диске и в резервной копии, но через API недоступна никому. `user-enable petya` снимает блокировку; прежние токены остаются отозванными, нужен новый токен или код приглашения.

Личная область отключённого пользователя. `tam-team --root /path/to/team-data user-export petya --out /path/to/petya.jsonl` выгружает все его личные записи (включая заменённые и удалённые) с авторством и полной историей, а также ещё не доставленные и доставленные заметки обучения из `learning.db`, в JSONL. Файл создаётся с правами 0600, существующий файл не перезаписывается. Выгрузка читает базы только на чтение и работает при запущенном сервере. `tam-team --root /path/to/team-data user-purge petya --confirm petya` удаляет каталог личной области и заметки обучения этого пользователя, ещё раз завершает его сессии, аннулирует коды приглашения и отзывает токены. Обе команды работают только для пользователя после `user-disable`. Удаление, как и `backup`, требует остановленного сервера: запущенный сервер или оставшийся процесс области обнаруживается по блокировке, и команда отказывает. В журнал администратора пишутся события `personal_exported` и `personal_purged` без содержимого записей. Командные и общие записи этого пользователя хранятся в других базах и остаются с прежним автором. Резервные копии, сделанные до удаления, по-прежнему содержат личную область; их нужно удалять или хранить отдельно по правилам компании.

Из checkout та же CLI: `PYTHONPATH=src python -m team_memory.cli ...`. В PowerShell сначала `$env:PYTHONPATH='src'`, затем `python -m team_memory.cli ...`. Эти команды не запускались против рабочей установки.

## Docker

Отдельный профиль не подключает том одиночной памяти:

```sh
docker compose -f docker-compose.team.yml config
docker compose -f docker-compose.team.yml build
docker compose -f docker-compose.team.yml run --rm team-memory python /app/src/team_memory/cli.py user-add vasya 'Вася'
docker compose -f docker-compose.team.yml run --rm team-memory python /app/src/team_memory/cli.py token-create vasya --client codex --out /team-data/vasya.token
docker compose -f docker-compose.team.yml up -d
```

Перед запуском проверить порт3738. Веб-интерфейс и `/mcp/` находятся на одном порту. Параметры: `.env`, `TAM_TEAM_PORT`, `TAM_TEAM_PUBLISH_HOST`, `TAM_TEAM_MAX_WORKERS`, `TAM_TEAM_OPERATION_TIMEOUT`, общие настройки LLM. Тома `tam-team-memory-data` и `tam-team-model-cache` можно переименовать переменными Compose. Не подключать старую рабочую БД как team-data: её перенос требует отдельной проверки владельца и резервной копии.

Серверный профиль использует внешнюю доступную модель, если включены LLM-задачи. Для Ollama адрес задаётся `OLLAMA_URL`; профиль добавляет `host.docker.internal:host-gateway` для доступа к хосту Docker на Linux. Настройка переопределяется через `TAM_TEAM_HOST_GATEWAY`. Наличие API-адаптера не означает, что выбранная модель поддерживает изображения.

## PostgreSQL вместо SQLite

С 14.6.0 командный сервер может хранить все данные во внешнем PostgreSQL 17+ (одна база на организацию, схема и собственная LOGIN-роль на каждую область, контрольные схемы `tam_control` и `tam_learning`). Личная установка всегда остаётся на SQLite. Выбор: шаг **Database** веб-мастера, раздел **Administration → Settings → Database** или `TAM_TEAM_DATABASE_URL` (DSN из дашборда имеет приоритет). Существующий SQLite-сервер переносится кнопкой **Migrate** (сухой прогон, режим обслуживания, копирование, проверка SHA-256 по каждой таблице, переключение, архив SQLite в `archive/sqlite-<ts>/`, откат с подтверждением названием организации) или без веб-интерфейса при остановленном сервере:

```sh
export TAM_TEAM_NEW_DSN='postgresql://tam:...@db.example.internal/tam?sslmode=verify-full'
tam-team --root /path/to/team-data db-check --dsn-env TAM_TEAM_NEW_DSN
tam-team --root /path/to/team-data db-migrate --dsn-env TAM_TEAM_NEW_DSN --dry-run
tam-team --root /path/to/team-data db-migrate --dsn-env TAM_TEAM_NEW_DSN
```

DSN передаётся только именем переменной окружения. Строки, нарушающие внешние ключи SQLite, не теряются: они попадают в таблицу `migration_quarantine` своей области, сухой прогон заранее показывает их число и примеры ключей. Требования к серверу, SQL для администратора БД, таблица управляемых PostgreSQL (RDS, Cloud SQL, Azure и другие), ограничения и отличия ранжирования: [TEAM_POSTGRES.md](TEAM_POSTGRES.md). Для пробного запуска: `docker compose -f docker-compose.team.yml -f docker-compose.team.postgres.yml up -d` (не для продакшена).

## Резервная копия и восстановление

SQLite: остановить сервер, затем выполнить:

```sh
tam-team --root /path/to/team-data backup --out /path/to/new-backup
tam-team --root /path/to/new-team-data restore --from /path/to/new-backup
```

В Docker те же подкоманды передаются `python /app/src/team_memory/cli.py` через `docker compose -f docker-compose.team.yml run --rm team-memory ...` после остановки сервиса; путь копии должен находиться на отдельном подключённом томе.

Копия содержит identity.db и SQLite-базы всех областей, включая авторство, историю и idempotency. Manifest содержит SHA256; проверяются SQLite integrity и внешние ключи. Активный сервер или оставшийся workspace-процесс блокирует offline-копирование. Восстановление принимает только новый каталог и публикует его после полной проверки; ошибка копирования не оставляет частично восстановленный сервер. Модели, файлы клиентских токенов и журналы не входят в копию. Клиентские токены хранить отдельно: хеши прав доступа восстанавливаются из identity.db.

PostgreSQL: те же команды работают без остановки сервера. `backup` делает `pg_dump` схем TAM из одного снимка и пишет manifest версии 2 с SHA-256 и числом строк каждой таблицы; `restore --from DIR --dsn-env VAR` восстанавливает в пустую базу, сверяет число строк и заново создаёт роли областей (роли не входят в дамп). Нужны `pg_dump`/`pg_restore` не старше сервера (в образе Docker есть клиент PostgreSQL 18) и тот же мастер-ключ. Для непрерывной защиты использовать PITR провайдера или архивацию WAL.

Непрерывная репликация (только SQLite) без остановки сервера и восстановление на момент времени (`--timestamp`) — через Litestream: `tam-team replication config|prepare|status|restore|drop|init-bucket`, sidecar `litestream` в профиле Compose `litestream` и локальное S3-хранилище в профиле `s3-local`. После `user-purge` реплику удалённой личной области нужно удалить командой `tam-team replication drop --user <id> --confirm <id>`: Litestream сам её не удаляет. Подробности, переменные `TAM_TEAM_REPLICA_*`, WAL и сроки хранения: [TEAM_BACKUP.md](TEAM_BACKUP.md).

## Лёгкий удалённый клиент

`src/team_memory/remote.py` использует только стандартную библиотеку Python. Его можно скопировать отдельно на macOS/Linux/Windows/WSL: модели, embedding-пакеты, Docker и фоновые службы на клиенте не нужны.

Переменные клиента: `TAM_REMOTE_URL` — конечный HTTPS endpoint `/mcp/`, `TAM_REMOTE_TOKEN_FILE` — путь к личному токену. Токен перечитывается для каждого запроса. Перенаправления отключены, чтобы не передать токен другому адресу. Локальный HTTP разрешён только для loopback.

Пример stdio-конфигурации IDE, поддерживающей `mcpServers`:

```json
{
  "mcpServers": {
    "total-agent-memory": {
      "command": "python3",
      "args": ["/absolute/path/remote.py"],
      "env": {
        "TAM_REMOTE_URL": "https://YOUR_SERVER/mcp/",
        "TAM_REMOTE_TOKEN_FILE": "/absolute/path/personal.token"
      }
    }
  }
}
```

На Windows использовать абсолютный путь к `python.exe` и Windows-пути. Для Codex эти же command/args/env переносятся в TOML-таблицу `mcp_servers.total-agent-memory`; формат конкретного клиента нужно соблюдать. Пакет также предоставляет команду `tam-remote`.

## Ограничения и диагностика

Число прогретых процессов по умолчанию3: личная, одна команда и общая область остаются загруженными одновременно. Операции выполняются последовательно. При меньшем лимите или большем числе областей поиск сначала обращается к уже загруженным процессам, затем открывает остальные; порядок результатов от этого не меняется. Старые процессы вытесняются при достижении TAM_TEAM_MAX_WORKERS. Больше прогретых процессов требует больше RAM; меньший лимит увеличивает холодные загрузки и CPU. При timeout сервер не повторяет запись автоматически: проверить историю перед повтором, поскольку завершение могло быть неопределённым.

Для конфигурации с тремя прогретыми MiniLM-процессами закладывать серверу минимум4ГиБ RAM и проверить расход на своей базе. В Linux ARM64 микропроверке сумма RSS workers составила1975MiB при3процессах и1315MiB при2; сумма RSS повторно учитывает общие страницы и не включает отдельный запас под gateway/БД/ОС. На маленькой машине задайте TAM_TEAM_MAX_WORKERS=1 или2 и учитывайте стоимость холодных загрузок. Нулевая CPU-нагрузка во время поиска не обещается.

Cross-encoder (`MEMORY_CROSS_RERANK`, по умолчанию `auto`) работает один раз на поиск, в процессе сервера: каждая область возвращает свои кандидаты без переранжирования (окно `MEMORY_CROSS_RERANK_WINDOW`, 50), сервер объединяет окна только тех областей, которые вызывающему разрешено читать, переранжирует объединённое окно и оставляет `limit` записей. Модель загружается в процессе сервера один раз и лениво; процессы областей её не загружают. Пока модель не готова (`auto`), при ошибке или по истечении `TAM_TEAM_OPERATION_TIMEOUT` остаётся порядок слияния. Ответ содержит `ordering` (`cross_rerank_then_score`) и `rerank` (`applied`, `not_ready`, `skipped`, `failed`, `timeout`). При `MEMORY_CROSS_RERANK=off` слияние прежнее: ранг внутри области, затем score.

Метрики счётчика запросов и гистограммы времени ведутся в сервисе; каждый вызов пишет структурированное событие без текста памяти и токена. Публичный health endpoint не показывает путь к данным или пользователей.

Веб-интерфейс: вход токеном, выбор области, поиск, просмотр страниц записей, сохранение, редактирование и история. Токен живёт только в памяти страницы.12сценариев прошли в Chromium/Firefox/WebKit, включая локальный dashboard. Нативные установки и фоновые службы Ubuntu/macOS/Windows проверены; расширенная CI-матрица остаётся отдельным этапом. Подробности: [проверки](benchmarks/browser-cpu-v14-20260915/RESULTS.md).
